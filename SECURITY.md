# Security policy

KathaSajha handles family accounts, children's first names, generated stories about real children,
and — once billing is enabled — payment sessions. Please treat findings here as you would for any
product involving minors.

## Reporting a vulnerability

**Do not open a public issue.**

Use **GitHub's private vulnerability reporting** on this repository: the *Security* tab →
*Report a vulnerability*. That channel is private to the maintainers and creates a draft advisory
we can work in.

Please include what you did, what happened, what you expected, and how severe you think it is.
A proof of concept helps enormously. If you are unsure whether something counts, report it — a
false alarm costs a few minutes, and the alternative does not.

Expect an acknowledgement within a few days. This is a small project without a paid security team,
so please allow reasonable time to fix before disclosing publicly. There is no bug bounty.

## Especially interested in

- Anything that lets one account read, modify or delete another account's stories or children
- Anything that exposes a child's name or a story to someone who should not see it, including
  through share links, social preview tags, PDFs, or log output
- Authentication and session handling — token forgery, session revocation that does not revoke,
  password reset token reuse
- Prompt injection that escapes the delimited input block and alters the story instruction
- Billing: webhook signature bypass, replayed or reordered events, granting a plan without payment
- Quota bypass, which is a direct financial exposure since every generation costs real money

## Out of scope

- Findings that require a compromised device or a malicious browser extension
- Missing hardening headers with no demonstrated impact
- Volumetric denial of service
- Reports generated by a scanner with no verified impact
- The known issues already recorded in [docs/TECH_DEBT.md](docs/TECH_DEBT.md) — please read it
  first, since several suspicious-looking things there are documented and deliberate

## Known and being addressed

Listed here so nobody spends time rediscovering them:

- **A `GOOGLE_API_KEY` was committed to git history** (commit `b3f882e`). The repository is public,
  and rewriting history does not un-publish it; the key must be rotated. Tracked in
  [docs/GO_LIVE.md](docs/GO_LIVE.md) as the first blocking item.
- **`/register` reveals whether an email is registered** by returning 409, while
  `/forgot-password` deliberately avoids exactly that leak. The customer list is enumerable.
- **`/api/health` is unauthenticated and verbose**, reporting environment and active providers.

## For anyone self-hosting a fork

The application refuses to boot in production rather than run half-configured, and those guards
exist because each failure mode is silent and expensive. Please do not remove them:

- A weak or default `SECRET_KEY`
- `EMAIL_BACKEND=console`, which prints password-reset links into the log and delivers nothing
- Partially configured Stripe credentials, which takes a customer's money and never upgrades them
- `IMAGE_PROVIDER=mock` alongside real story generation, which serves placeholder art as if it
  were the product

Set `TRUSTED_PROXY_IPS` to your actual proxy. It ships empty, which means `X-Forwarded-For` is not
believed at all — deliberate, because trusting it unconditionally lets anyone rotate the header and
walk straight past the IP-keyed rate limits.
